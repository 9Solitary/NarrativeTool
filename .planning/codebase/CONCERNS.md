# Codebase Concerns

**Analysis Date:** 2026-07-23

## Tech Debt

### Monolithic Source Files

- Issue: The entire application logic is spread across two enormous monolithic JavaScript files -- `NarrativeCanvas/app.js` (27,009 lines) and `NarrativeCanvas/main.js` (29,033 lines) -- plus `NarrativeCanvas/canvas.css` (8,102 lines) and `NarrativeCanvas/styles.css` (8,046 lines). No module system, no file-level separation of concerns. All app logic (rendering, state management, event handling, export, AI integration, serialization, DOM manipulation) lives in one flat namespace.
- Files: `NarrativeCanvas/app.js`, `NarrativeCanvas/main.js`, `NarrativeCanvas/canvas.css`, `NarrativeCanvas/styles.css`
- Impact: Extremely difficult to reason about, test in isolation, or modify without unintended side effects. New contributors face a steep learning curve. Merge conflicts are likely on any concurrent change to the same file.
- Fix approach: Extract subsystems (rendering, state management, export, AI, serialization) into separate ES modules. Use a build step to bundle for Obsidian's CommonJS environment. Prioritize extracting the canvas rendering engine and the export/Runtime JSON pipeline first, as those are the most self-contained subsystems.

### Code Duplication Between app.js and main.js (Bundled Copy)

- Issue: `NarrativeCanvas/main.js` contains a verbatim bundled copy of `NarrativeCanvas/app.js` (25,227 lines) inside the `installNarrativeCanvasApp()` function (lines 2076-29033). The build script `NarrativeCanvas/scripts/build-plugin-bundle.cjs` replaces this section during the plugin packaging step. This means every constant, function, and type definition appears twice in the repository: once in `app.js` (the standalone browser build source of truth) and once in `main.js` (the pre-bundled Obsidian plugin copy).
- Files: `NarrativeCanvas/app.js` lines 1-27009, `NarrativeCanvas/main.js` lines 2076-29033, `NarrativeCanvas/scripts/build-plugin-bundle.cjs`
- Impact: The `main.js` bundled copy can drift out of sync if someone edits it directly instead of running the build script. The `--check` mode in `build-plugin-bundle.cjs` and CI verification aim to catch this, but any direct edits to `main.js` outside the plugin-specific preamble (lines 1-2075) will be overwritten by the next build. This is confusing to new developers.
- Fix approach: Consider making `main.js` the build artifact only (gitignored, generated in CI) and keeping `main-plugin.js` as the handwritten plugin layer. Alternatively, explicitly document in a top-level comment that `installNarrativeCanvasApp()` body is auto-generated.

### Build-Generated Artifacts Committed to Git

- Issue: `NarrativeCanvas/main.js` and `NarrativeCanvas/styles.css` are build artifacts (generated by `NarrativeCanvas/scripts/build-plugin-bundle.cjs` and `NarrativeCanvas/scripts/build-plugin-styles.cjs` respectively) but are committed to version control. These files together total over 37,000 lines of generated code. The CI `verify-plugin-artifacts` workflow exists specifically to detect staleness.
- Files: `NarrativeCanvas/main.js` (lines 2076-29033), `NarrativeCanvas/styles.css` (lines ~8,046)
- Impact: PR reviews are polluted with massive diffs whenever `app.js` or `canvas.css` changes. Git blame is meaningless for most of these files. The CI check may fail if a developer forgets to run the build scripts before pushing.
- Fix approach: Identified as a deliberate trade-off -- the built artifacts are committed so the repo is directly consumable as an Obsidian `.obsidian/plugins/` installation without a build step. This is a pragmatic choice for Obsidian plugin distribution. If changing this practice, the alternative is a release-only approach with CI-generated ZIP artifacts.

### Manual CSS Scoping for Plugin Isolation

- Issue: `NarrativeCanvas/scripts/build-plugin-styles.cjs` implements a custom CSS parser that rewrites all CSS selectors to scope them under `.narrative-canvas-plugin-host`. This is a hand-rolled CSS parser (brace matching, string/comment tracking, selector splitting) with 170 lines of parsing logic. It must exactly handle all CSS syntax including `:is()`, `[data-*="x,y"]` comma-in-selectors edge cases, and `@media`/`@supports` at-rule nesting.
- Files: `NarrativeCanvas/scripts/build-plugin-styles.cjs`, `NarrativeCanvas/plugin.css`
- Impact: This parser is fragile. Any CSS construct it does not handle (e.g., `@container`, `@layer` nested rules, `:has()`, `@scope`) will either break the build or leave selectors unscoped, causing CSS leaks into the Obsidian host UI or vice versa. The self-test at line 117-121 covers only the comma-in-selectors case.
- Fix approach: Consider using PostCSS with a custom plugin for selector prefixing, or use `@scope` CSS at-rule where browser support allows. At minimum, add a comprehensive selector-scoping test suite covering all currently-used CSS features.

### Legacy Format Support Accumulation

- Issue: Significant code exists to handle legacy/migrated formats. This includes: `LEGACY_PROJECT_FILE` (`NarrativeCanvas/project.json`), `LEGACY_JSON_EXTENSION` (`.json`), `RETIRED_NODE_TYPES` (`Condition`, `Set`), `LEGACY_PLAYBOOK_ACTION_OPERATION_VALUES` (`if`, `goTo`, `show`, `hide`, `lockChoice`, `unlockChoice`), `LEGACY_EVENT_FRAME_COLORS`, `LEGACY_DEFAULT_NODE_BADGES`, `JS_CONDITION_LEGACY_FUNCTIONS` (`has`, `contains`), and `LEGACY_DEFAULT_NODE_BADGES`. The app also supports `Condition` and `Set` node types by auto-converting them to `Content` on load.
- Files: `NarrativeCanvas/app.js` lines 22, 41-42, 83-84, 154-155, 338, 22686-22711, `NarrativeCanvas/main.js` lines 6, 92, 509, 2099-2100, 24708-24733
- Impact: Carrying legacy format support indefinitely bloats the codebase and complicates the type system. Every new feature must account for these legacy paths. The `RETIRED_NODE_TYPES` auto-conversion on load is silent and may mask data integrity issues.
- Fix approach: Define a deprecation timeline. After a major version bump (e.g., 2.0), drop support for `.json` extension projects and `NarrativeCanvas/project.json` loading. Add a one-time migration tool to upgrade legacy projects to the current format.

### AI API Key Stored in Plugin's data.json

- Issue: The AI API key is stored in Obsidian's plugin data (`data.json`) in plain text via `this.plugin.settings.aiApiKey`. The settings UI uses `input.inputEl.type = "password"` to mask the input field, but the value is written unencrypted to disk.
- Files: `NarrativeCanvas/main.js` lines 38, 188, 205, 1151, 1166
- Impact: Anyone with filesystem access to the Obsidian vault can read the API key from `.obsidian/plugins/narrative-canvas/data.json`. If the vault is synced (e.g., via Obsidian Sync, git, or cloud storage), the key is exposed.
- Fix approach: The current behavior is documented in the settings UI ("Stored in this plugin's local data.json."). For improved security, consider using Obsidian's `loadData`/`saveData` with encryption, or delegate to the OS keychain. At minimum, add a warning in the README about this behavior.

### Web-Build localStorage AI Config for Standalone Mode

- Issue: In the standalone browser build (`NarrativeCanvas/app.js`), the AI configuration including the API key is stored in `localStorage` under the key `narrative-canvas-ai-config`. The `getWebAiConfig()` function reads this directly. The plugin build replaces these functions with stubs, so this only affects the browser/web deployment.
- Files: `NarrativeCanvas/app.js` lines 9626-9639, `NarrativeCanvas/scripts/build-plugin-bundle.cjs` lines 141-158
- Impact: localStorage is accessible to any JavaScript running on the same origin. Cross-site scripting (XSS) vulnerabilities would expose the key. Since this is a single-page app loading from the local filesystem, the attack surface is limited but non-zero.
- Fix approach: For the standalone web build, warn users that AI configuration is stored in plain text in browser storage. Consider session-only storage or requiring the key to be entered each session.

## Known Bugs

### Console Error Logging in Production

- Issue: There are 34 `console.error` calls in `NarrativeCanvas/main.js` and 24 in `NarrativeCanvas/app.js`. Many of these are in catch blocks that re-throw or silently swallow errors. A few are in production code paths (not just development debugging). All `console.error` calls remain active in the shipped plugin, polluting the Obsidian developer console.
- Files: `NarrativeCanvas/main.js` lines 102, 135, 139, 152, 182, 270, 296, 334, 4567, 5696, 6674, 6775, 10598-10600, 10639, 14158, 20423, 20466, 20503, 20542, 20577, 20686, 20751, 20771, 20902, 20935, 20943, 23349
- Impact: Users with the developer console open see error noise that may be confusing or alarming. Some of these errors may indicate real problems but are logged without user-facing alerts.
- Workaround: Wrap console logging behind a debug flag that defaults to off in production builds.

### Generic Error Handling Hides Failure Causes

- Issue: Most try/catch blocks follow the pattern `catch (error) { console.error(error); }` without any user-facing feedback. The `reportCommandError` function (line 181-183) shows a generic "[command name] failed." notice, discarding specific error details. The AI error path (lines 190, 207) throws `new Error("Configure AI endpoint, API key, and model in Narrative Canvas settings.")` which is a validation check, not an actual error recovery path.
- Files: `NarrativeCanvas/main.js` lines 181-183, 701-711, `NarrativeCanvas/app.js` multiple locations
- Impact: When operations fail, users receive no actionable information. Bug reports will lack diagnostic detail.
- Workaround: At minimum, surface the error message in user-facing notices. A structured error-reporting mechanism with error codes would greatly improve debuggability.

### AI Stream Handling Fragility

- Issue: The AI streaming implementation uses manual byte-level parsing of Server-Sent Events (SSE) from a raw `fetch` response body. The parser (`readAiEventStream` in `NarrativeCanvas/app.js` lines 9879-9907, and the plugin version in `NarrativeCanvas/main.js` lines 221-248) manually splits by `\r?\n`, detects `data:` prefixes, and handles `[DONE]` markers. The `JSON.parse` inside the stream reader loop silently catches parse errors (`catch (_error) { /* Ignore provider keep-alive or non-JSON event rows. */ }`), meaning malformed events are silently discarded.
- Files: `NarrativeCanvas/app.js` lines 9879-9907, 9910-9917, `NarrativeCanvas/main.js` lines 203-248
- Impact: If an AI provider changes their SSE format, streamed content may be silently truncated or mangled without any error indication. The silent catch also hides JSON parse errors that could indicate genuine protocol mismatches.
- Fix approach: Track the number of discarded events and surface a warning if more than a threshold are skipped. Log the first few skipped payloads at debug level to aid troubleshooting. Consider using a dedicated SSE parser library.

### AbortController Leak in AI Requests

- Issue: The `sendAiMessage()` function in `NarrativeCanvas/app.js` (line 9929) creates a new `AbortController` on every call. The `state.aiAbortController` is overwritten, but any previous controller that wasn't explicitly aborted may leak if the old request never completes. The timeout-based abort (`window.setTimeout` at line 9947) fires after 120 seconds, but if the user sends rapid messages, intermediate controllers are overwritten before their timeout fires.
- Files: `NarrativeCanvas/app.js` lines 9940-9949
- Impact: Memory leak from un-aborted controllers; potential for stale requests to continue consuming resources after they are no longer needed.
- Fix approach: Abort the previous controller (if any) before creating a new one at line 9940.

## Security Considerations

### API Key Storage in Plain Text

- Risk: The AI provider API key is stored unencrypted in Obsidian's plugin data file.
- Files: `NarrativeCanvas/main.js` lines 38, 1151, 1166
- Current mitigation: The settings UI uses `type="password"` to hide the key from shoulder-surfing. The `data.json` file is inside the `.obsidian/` directory which is typically gitignored by Obsidian's default setup. The README and settings UI transparently document that the key is "Stored in this plugin's local data.json."
- Recommendations: If this is a fork intended for an internal toolchain (`ObsidianNarrativeToolchain.md`), this is an acceptable trade-off. For public distribution, consider encrypting the key with a vault-derived key or using the OS credential store.

### innerHTML Usage for Dynamic Content

- Issue: The codebase uses `innerHTML` for rendering dynamic content extensively (47 occurrences in `app.js`, 47 in `main.js`). While most content is project data authored by the user, the AI chat panel renders AI-generated markdown into HTML using a custom markdown renderer (`renderAiMarkdown` in `NarrativeCanvas/app.js` lines 9666-9796, and the bundled copy in `main.js`). The markdown renderer applies `escapeHtml` to most content but constructs HTML strings via string interpolation.
- Files: `NarrativeCanvas/app.js` lines 9642-9796, 9666-9796, multiple `innerHTML` assignments across both files.
- Impact: If the AI provider returns malicious content, or if a user loads a crafted `.ncanvas` project file, XSS is theoretically possible through unescaped HTML in rendered fields. The `escapeHtml` utility at line 26990-26996 covers `<`, `>`, `&`, `"`, `'`, but the markdown renderer's link handling (`renderAiMarkdownInline`, lines 9647-9655) constructs `<a>` tags from user/AI content.
- Current mitigation: `escapeAttr` is used for URL and title attributes. `escapeHtml` is applied to link labels. Attribution strings are escaped.
- Recommendations: Audit all `innerHTML` call sites for unescaped user or AI content. Consider using `textContent` or DOM-building APIs where possible. Add a Content Security Policy header for the standalone web build.

### Function Constructor in Scripts

- Issue: `NarrativeCanvas/scripts/portable-export-acceptance.cjs` uses `Function()` constructor at line 2345 to dynamically evaluate condition expressions during testing. `NarrativeCanvas/scripts/verify-plugin-artifacts.cjs` uses `Function()` at line 114 to parse translation source code. Neither file is shipped in the plugin, so this only affects development/CI.
- Files: `NarrativeCanvas/scripts/portable-export-acceptance.cjs` line 2345, `NarrativeCanvas/scripts/verify-plugin-artifacts.cjs` line 114
- Risk: Low (development tools only, not shipped to users). The `Function()` constructor has the same security implications as `eval()`.
- Recommendations: Acceptable for test scripts. No change needed for the plugin.

### No Content Security Policy

- Issue: `NarrativeCanvas/index.html` has no Content Security Policy `<meta>` tag or HTTP header. The app loads scripts and styles from local files, but the AI fetch makes outbound requests to a user-configured endpoint.
- Files: `NarrativeCanvas/index.html`
- Impact: If the web build is ever served from a remote origin, it would be vulnerable to script injection. Currently mitigated by the fact that the web build is opened from the local filesystem.
- Recommendations: Add a CSP for the web build at minimum. For the plugin build (which runs inside Obsidian's Electron webview), CSP is less critical as Obsidian controls the environment.

## Performance Bottlenecks

### Full Document Query Selectors in Render Functions

- Issue: Rendering functions use `document.querySelector` and `dom.scope.querySelector` extensively to locate DOM elements. For example, the status bar update at `updateStatus()` (line 28904) makes multiple querySelector calls. The canvas rendering pipeline triggers re-renders that re-query DOM elements frequently.
- Files: `NarrativeCanvas/app.js` / bundled in `NarrativeCanvas/main.js` (lines 28904-28931, and many render functions)
- Impact: In large projects with hundreds of nodes, DOM queries during re-renders may cause jank. The current canvas uses a manual DOM-based approach (not Canvas API or WebGL), so every node is a DOM element.
- Cause: DOM-based rendering with frequent layout-triggering queries. No virtual DOM or diffing; the code manually manages DOM updates.
- Improvement path: Cache DOM references in the `dom` object (already done for major elements). Consider batching DOM reads/writes with `requestAnimationFrame`, which is already used for canvas viewport rendering via `state.canvasViewportRenderFrame` (line 11237-11238). For very large canvases, consider a virtualized node list that only renders nodes within the viewport.

### String-Based State Serialization on Every Save

- Issue: Project saves involve `JSON.stringify(createBlankSavedState(...))` and `JSON.stringify(state.project...)` on every save operation. For large projects with thousands of nodes, serialization can be expensive.
- Files: `NarrativeCanvas/main.js` lines 498-518, `NarrativeCanvas/app.js` save functions
- Current mitigation: Auto-save is configurable (default interval of 0 = off, falling back to 2 seconds when active). History is limited to 80 entries (`HISTORY_LIMIT = 80`).
- Improvement path: Consider incremental/delta-based saves for auto-save. Use `JSON.stringify` with a replacer that skips unchanged data. The current approach is acceptable for typical usage but may degrade with very large projects.

### No Debouncing on Rapid User Actions

- Issue: Several user interactions (node moves, text input in inspectors) trigger immediate state updates and re-renders without debouncing. While the canvas viewport uses `requestAnimationFrame` scheduling, property inspector changes appear to trigger synchronous updates.
- Files: `NarrativeCanvas/app.js` inspector event handlers (various locations)
- Impact: Rapid typing in node property fields or quick node repositioning may cause jank on lower-powered devices.
- Improvement path: Debounce state updates from text input fields by 150-300ms.

## Fragile Areas

### Canvas Rendering Pipeline

- Files: `NarrativeCanvas/app.js` functions related to canvas rendering, `NarrativeCanvas/canvas.css` (all 8,102 lines)
- Why fragile: The rendering is tightly coupled to the DOM structure defined in `NarrativeCanvas/index.html`. CSS class names, element hierarchies, and inline styles are spread across JS and CSS with implicit contracts. The CSS is also auto-scoped for the plugin build, so changes to `canvas.css` must be tested in both standalone web and Obsidian plugin contexts.
- Safe modification: Always run `node scripts/build-plugin-bundle.cjs` and `node scripts/build-plugin-styles.cjs` after any CSS or rendering changes. Test in both contexts. Avoid changing DOM structure without updating all querySelector calls.
- Test coverage: The smoke test (`NarrativeCanvas/tests/smoke.html`, 2,213 lines, 369 assertions) and GUI regression test (`NarrativeCanvas/tests/gui-regression.html`, 997 lines, 124 assertions) cover basic canvas operations. The fixture roundtrip test (`NarrativeCanvas/tests/fixture-roundtrip.html`, 918 lines, 156 assertions) validates project load/save integrity. However, there are no visual regression tests (screenshot comparison).

### Export / Runtime JSON Pipeline

- Files: `NarrativeCanvas/docs/runtime-json.schema.json`, `NarrativeCanvas/docs/export-profile.schema.json`, `NarrativeCanvas/docs/portable-acceptance-summary.schema.json`, `NarrativeCanvas/docs/portable-route-cases.schema.json`, `NarrativeCanvas/docs/story-layout.schema.json`, `NarrativeCanvas/docs/state-schema.schema.json`, `NarrativeCanvas/scripts/portable-export-acceptance.cjs`
- Why fragile: The export system produces multiple output formats (Runtime JSON, Portable acceptance, Twee/SugarCube, Story Markdown) from the same internal project model. Any change to the project state structure must update all export paths and their corresponding JSON schemas. The `portable-export-acceptance.cjs` script (2,462 lines) is a comprehensive acceptance test that validates export correctness but is complex enough to be fragile itself.
- Safe modification: Run `node scripts/portable-export-acceptance.cjs` after any changes to the project model or export logic. Update all affected JSON schemas in `NarrativeCanvas/docs/` simultaneously.
- Test coverage: Good -- the portable export acceptance test is thorough. However, it requires a running browser (uses Puppeteer-like headless Chrome) and is therefore not a fast unit test.

### AI Integration

- Files: `NarrativeCanvas/app.js` lines 9626-9980, `NarrativeCanvas/main.js` lines 38-39, 186-269, 1143-1167
- Why fragile: The AI integration uses raw `fetch` with streaming SSE parsing. There are two independent implementations: one for the plugin (using Obsidian's `requestUrl` for non-streaming and raw `fetch` for streaming) and one for the web build (using browser `fetch`). The streaming parser makes assumptions about the SSE format that may break with different AI providers. The build script stubs out the web-only functions in the plugin bundle.
- Safe modification: Test AI features with multiple providers (OpenAI-compatible endpoints). The streaming parser at `NarrativeCanvas/app.js` line 9879 should be factored out into a testable pure function.
- Test coverage: Minimal. There are no automated tests for AI functionality beyond basic smoke testing.

### Build Pipeline

- Files: `NarrativeCanvas/scripts/build-plugin-bundle.cjs` (195 lines), `NarrativeCanvas/scripts/build-plugin-styles.cjs` (170 lines), `NarrativeCanvas/scripts/verify-plugin-artifacts.cjs` (344 lines)
- Why fragile: Both build scripts use hand-rolled source code manipulation -- `build-plugin-bundle.cjs` replaces function bodies via regex + brace matching, and `build-plugin-styles.cjs` parses CSS for selector scoping. Neither uses a proper AST. The build scripts throw errors if their expected patterns are not found (lines 163, 177, 182), which is good for catching issues but means any structural change to the source files can break the build.
- Safe modification: When renaming or restructuring functions in `app.js` that are referenced by the build script (`loadWebState`, `saveWebState`, `getWebProjectStorage`, `clearBrowserStorageFromUi`, `clearBrowserStorageConfirmed`, `getWebAiConfig`, `saveWebAiConfig`, `requestWebAiCompletion`), update the regex patterns in `build-plugin-bundle.cjs` lines 106-158 simultaneously. When changing CSS structure, verify `build-plugin-styles.cjs` still produces correct output.
- Test coverage: `verify-plugin-artifacts.cjs` runs `--check` mode on both build scripts, plus validates translations, locale coverage, and schema consistency. This is run in CI on every PR and push to main.

## Scaling Limits

### Node Count Scalability

- Current capacity: Designed for "hundreds of nodes" per project. The `NarrativeCanvas/docs/export-portability.md` mentions "large-canvas" fixtures. The board dimensions are 4000x2600 (`BOARD_WIDTH`, `BOARD_HEIGHT`).
- Limit: DOM-based rendering means each node creates multiple DOM elements. At ~1000+ nodes, the browser will struggle with layout and painting. Node lookup is O(n) in several code paths (e.g., `state.project.nodes.find(...)`).
- Scaling path: Implement a spatial index (quadtree or grid) for node lookup. Virtualize node rendering to only create DOM elements for nodes visible in the viewport. The frame containment index (`FRAME_CONTAINMENT_INDEX_CELL_SIZE = 1024`) already hints at spatial partitioning being considered.

### History/Undo Stack Memory

- Current capacity: `HISTORY_LIMIT = 80` entries. Each entry is a full project state snapshot.
- Limit: For large projects, 80 full state snapshots consume significant memory. Each snapshot includes all nodes, links, characters, variables, and UI state.
- Scaling path: Implement a command-pattern undo system that stores only deltas (what changed) rather than full snapshots. This would allow more undo steps with less memory.

## Dependencies at Risk

### Obsidian API Stability

- Risk: The plugin depends on Obsidian's internal API (`require("obsidian")`). The plugin declares `minAppVersion: "1.5.0"` in `manifest.json` and `isDesktopOnly: true`. Obsidian's API is not versioned with semantic versioning, and breaking changes can occur in minor releases.
- Impact: A future Obsidian update could break the plugin's view registration, file system access, or command palette integration.
- Files: `NarrativeCanvas/main.js` line 1 (Obsidian imports), `NarrativeCanvas/manifest.json`
- Migration plan: The `NarrativeCanvas/versions.json` file maps plugin versions to minimum Obsidian versions (currently all map to 1.5.0). Monitor Obsidian's release notes and test against beta releases. The plugin only uses stable, documented APIs (`Plugin`, `ItemView`, `PluginSettingTab`, `Setting`, `Notice`, `TFile`, `TFolder`, etc.), which reduces risk.

### No External Runtime Dependencies

- Risk: The project has zero npm dependencies -- it is pure vanilla JavaScript with no package.json for the plugin. The `scripts/` directory uses Node.js built-ins only (`fs`, `path`, `child_process`, `url`, `os`). This is by design for Obsidian plugin compatibility.
- Impact: All utility functions (deep cloning, debouncing, string escaping, etc.) are hand-written inline, which is both a strength (no supply chain risk) and a weakness (reinventing wheels, potential for bugs in custom implementations).
- Files: `NarrativeCanvas/app.js` utility functions at the end of the file (e.g., `clamp` at line 26986, `escapeHtml` at line 26990, `slugify` at line 26982)
- Migration plan: None needed for the plugin core. For the broader toolchain project (`ObsidianNarrativeToolchain.md`), new plugins (`flow-tools`, `export-dialogue`, `graph-tools`) may benefit from shared utility packages in a `shared/` directory as proposed.

## Test Coverage Gaps

### No Unit Tests for Core Logic

- What's not tested: Core logic functions (state management, node operations, link operations, serialization/deserialization, condition evaluation, Playbook engine) have no isolated unit tests. All tests are browser-based end-to-end tests that run through the full app.
- Files: All logic in `NarrativeCanvas/app.js` (27,009 lines)
- Risk: Refactoring any core logic risks introducing regressions that only manifest in specific project states. Browser-based tests are slow and cannot cover all edge cases.
- Priority: High. As the toolchain expands (`ObsidianNarrativeToolchain.md`), the need for a stable core will increase. Extracting the state management and serialization logic into testable modules would be the highest-impact improvement.

### No Test for Godot Runtime Loader

- What's not tested: The Godot runtime loader example at `NarrativeCanvas/examples/godot-runtime-loader/NarrativeCanvasRuntime.gd` has no automated tests. This is the primary export target for the toolchain project.
- Files: `NarrativeCanvas/examples/godot-runtime-loader/NarrativeCanvasRuntime.gd`, `NarrativeCanvas/examples/godot-runtime-loader/RuntimeRouteDemo.gd`
- Risk: Export format changes could silently break Godot compatibility. The `ObsidianNarrativeToolchain.md` Phase 2 specifically targets "Verify Godot can read" exported dialogue files.
- Priority: Medium. Tests should be added in Phase 2 of the toolchain project. A test that exports a known `.ncanvas` project and validates the `.dialogue` output parses correctly in Godot would catch regressions early.

### Limited Cross-Browser Testing

- What's not tested: The test runner (`NarrativeCanvas/scripts/run-browser-test.cjs`) only supports Chromium-based browsers. There are no Firefox or Safari test runs in CI. The plugin is `isDesktopOnly: true`, so mobile browsers are not relevant, but Electron (which Obsidian uses) is Chromium-based, making this acceptable.
- Files: `NarrativeCanvas/scripts/run-browser-test.cjs` lines 27-42 (browser detection)
- Risk: Low for the Obsidian plugin use case. Higher if the standalone web build is expected to work across browsers.
- Priority: Low.

### No Performance Regression Testing

- What's not tested: The perf test (`NarrativeCanvas/tests/perf.html`, 304 lines, 9 assertions) runs basic timing checks but does not establish performance budgets or compare against historical baselines.
- Files: `NarrativeCanvas/tests/perf.html`
- Risk: Performance regressions may go unnoticed until users report them.
- Priority: Medium. Add performance budgets for key operations (project load, save, node rendering, undo) and integrate them into CI.

## Missing Critical Features (Gap to Toolchain Vision)

### No Flow/Fragment Layer Yet

- Problem: The `ObsidianNarrativeToolchain.md` planning document describes a "Flow -> Flow Fragment -> Dialogue -> Dialogue Fragment" hierarchy, with Flow and Flow Fragment implemented via Obsidian's native `.canvas` files. None of this has been implemented yet.
- Blocks: The entire "Flow Tools" plugin (Phase 3) -- Flow navigation, Flow Fragment support, bidirectional Flow-to-Dialogue linking.
- This is a planned feature gap, not a missing feature in the current plugin. The `NarrativeCanvas/` directory is explicitly only the Dialogue layer (Layer 3-4).

### No Godot Dialogue Manager Export

- Problem: While the plugin can export Runtime JSON, Twee/SugarCube, and Story Markdown, there is no Godot Dialogue Manager (`.dialogue`) export format.
- Blocks: Phase 2 of the toolchain project.
- The export infrastructure (JSON schemas, portable acceptance testing) provides a solid foundation for adding a Godot export profile.

### No Project-Level Global Index

- Problem: The `ObsidianNarrativeToolchain.md` Phase 4 envisions a "Narrative Project" plugin that provides project configuration, batch export, build, global indexing, and project settings. None of this infrastructure exists.
- Blocks: Graph View integration, batch export, project-wide search.
- This is explicitly a Phase 4 (later-stage) feature.
